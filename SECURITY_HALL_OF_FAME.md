## Maintainer-Identified Findings

Vulnerabilities the project maintainer found through their own internal review, rather than an external report, are logged here separately so the table above stays accurate to who actually disclosed each one.

| Finding | Contribution | Date |
| :--- | :--- | :--- |
| **Bertuğ Fahri ÖZER** (project maintainer, internal audit — not an external report) | Identified that `Methods::moduleUpload()`/`moduleCreate()`/`moduleDelete()` were gated only by a single, delegable `create`/`delete` permission role, even though uploading a module ZIP is uploading PHP code that `app/Config/Routes.php` `require`s unconditionally on the next request — a delegated permission holder could reach remote code execution, or use the create/delete endpoints to write or drop arbitrary module files and tables. Closed with a hardcoded `inGroup('superadmin')` gate on all three controller methods. | Sep 2026 |
| **Bertuğ Fahri ÖZER** (project maintainer, internal audit — not an external report) | Identified that `Methods::update()` wrote an `auth_permissions_pages` row's `pagename`, `className`, `methodName` and `typeOfPermissions` with no actor-scope check at all — exactly the four columns `Ci4MsAuthFilter` reads on every request to decide authorization (`className`+`methodName` locate the row, `permission_string($page->pagename, ...)` and `typeOfPermissions` decide the verdict), and the existing `classNameMethodNameCollides()` guard only stopped a duplicate `(className, methodName)` pair, not a `pagename`/`typeOfPermissions` change on an existing row. A delegated permission-page editor could therefore remap any route's authorization to a permission they already held, effective immediately since `update()` already calls `rbac_cache_flush()`. Closed with a hardcoded `inGroup('superadmin')` gate on `create()`, `update()` and the POST+AJAX branch of `index()`, plus `PROTECTED_MODULES` enforcement extended to `update()` and `index()`'s POST branch (both the `module_id` and `page_id` paths), applied even to superadmin; `index()`'s GET branch was left open so `read`-permitted operators keep the list screen. | Sep 2026 |
| **Bertuğ Fahri ÖZER** (project maintainer, internal audit — not an external report) | Identified that the backend login captcha could be skipped entirely by omitting the `captcha` field: `LoginController::loginAction()` compared the submitted value to the expected one with a loose `==`, the expected phrase exists only in one-request flashdata written by the login form's GET, and Shield's `getLoginRules()` carries no captcha rule — so a client that never fetched the form sent `null` against an expected `null`, and `null == null` passed. Both layers were open at once; a session and CSRF token obtainable from any other page was enough. Closed with a `captcha => required` validation rule plus a fail-closed comparison (`hash_equals()`, empty expected value rejected). Project CVSS assessment: `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N` = **5.3**, modelling the lost anti-automation control (credential stuffing, CWE-804 / CWE-307) rather than an authentication bypass — login still required the correct password; read literally as no direct C/I/A impact the same flaw scores 0.0. The `auth-rates` throttle stayed in force. Details in `CHANGELOG.md`. | Oct 2026 |
| **Bertuğ Fahri ÖZER** (project maintainer, internal audit — not an external report) | Identified that `Modules\Auth\Config\AuthConfig` exempted two state-changing lock-screen POSTs from CSRF via `$csrfExcept = ['backend/lock', 'backend/lock/*']`: `POST backend/lock` (`LockController::unlockAction()`, which logs out and destroys the session on the third failed attempt) and `POST backend/lock/set` (`setLockAction()`, which locks the session). `SameSite=Lax` was the only remaining defence. A defense-in-depth gap rather than a standalone bypass, since `SameSite=Lax` already blocked a plain cross-site POST. Closed by emptying `$csrfExcept`; CI4's own `Filters::initialize()` confirms both routes now carry the `csrf` before-filter. Project CVSS assessment: `CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:N/I:N/A:L` = **3.1**, with `AC:H` for the `SameSite=Lax` barrier (an attack needs a same-site foothold or a browser that does not enforce Lax), `UI:R` for the victim opening attacker content, and `A:L` for forced session termination or locking with no data read or modified. Details in `CHANGELOG.md`. | Oct 2026 |
